### #59 · message_id 口径：轮次相关键，非 chat_message 自增主键

- **文档现状**：04 §3.2 代码注释（行 534）"messageId：会话层保存 USER 消息后取得的自增主键"。
- **矛盾所在**：与 §3.4 v1.2 注（决策 #52）直接冲突——saveAll 快照替换语义下 chat_message 的唯一写入方是记忆仓储：MessageChatMemoryAdvisor 的 before() 自动把新用户消息 add 进记忆、after() 落 AI 回复（1.1.2 sources 核实），会话层预存 USER 消息会导致 ①提示词消息重复（advisor 再注入一次）②其自增 id 每轮先删后插，作为日志外键跨轮必悬挂。
- **实现现状**：`ai/log/MessageIdGenerator` 生成时间戳锚定的进程内单调 long 作"轮次相关键"，intent_classify_log 与 tool_call_log 的 message_id 均用它（本轮唯一、可按轮聚合，满足"意图准确率/工具成功率"两指标的统计口径）；chat_message.tool_calls 摘要由会话层在流结束后对最新 AI 消息做一次收尾 UPDATE（content 写入仍由 saveAll 独占）。另：IntentAgent 实现以 `content()` + Jackson 手动解析替代示例中的 `.entity()`，为精确区分 PARSE/TIMEOUT 降级分支并剥除 markdown 围栏，语义等价。
- **文档动作**：04 §3.2 注释替换 + 新增注②（P7、P8）。行 16 的 v1.2 修订记录含旧口径表述，属历史记录不改。

### #60 · tool_start/tool_end 的观测点：ToolCallingManager 装饰器

- **文档现状**：总体设计 §3.2 第 8 步（"toolCallId 来自模型返回的 tool_call 协议字段，由 Spring AI 解析后透传"）暗示可从 ChatClient 外层流观测工具事件；04 §3 未展开。
- **核实证据**（SAA 1.1.2.1 DashScopeChatModel 源码）：默认内联执行（internalToolExecutionEnabled=true）时，工具在模型内部循环执行（chatResponse.flatMap → toolCallingManager.executeToolCalls → internalStream 续跑），**工具调用块与 ToolResponseMessage 块不进入外层 Flux**；且 `Generation.getOutput()` 静态类型为 AssistantMessage、ToolResponseMessage 是其兄弟类，流侧无从按类型识别。
- **实现现状**：`ObservableToolCallingManager` 装饰 DefaultToolCallingManager（自定义 bean 存在后 spring-ai 自动配置退避，DashScopeChatModel 注入装饰器）——工具执行环是"模型请求的 toolCallId"与"执行结果"唯一同框的位置；通知器（ToolEventNotifier）经 toolContext 调用级传入（仅聊天流式调用携带，IntentAgent 等无工具调用不受影响）；tool_call_log 落库同在工具层（ToolCallLogger 包装）。
- **文档动作**：04 §3.3 末补观测点说明（P9）。

### #61 · 索引 Schema 需声明 doc_id TAG；Schema 变更须 DROPINDEX 重建

- **文档现状**：04 §3.1.1 仅声明 kb_type（行 518）；而总体设计 §3.4 重建管道要求"删除旧向量（按 docId）"——无对应 Schema 声明。

- **文档动作**：04 §3.1.1 代码注释 / 代码行 / bullets 三处更新（P4–P6）。

### #65 · SSE 异步分发的 SecurityContext 持久化（附录 A1 升格，v1.1）

- **现象**（M1-5 编码实测）：每条 SSE 流结束产生 2 条 ERROR——Tomcat 的 ASYNC dispatch 带空 SecurityContext 重跑授权规则，试图向已提交响应写 401（"Unable to handle the Spring Security Exception because the response is already committed"）。
- **根因**：① OncePerRequestFilter 默认 `shouldNotFilterAsyncDispatch()=true`——JWT 过滤器跳过再分发，而 SecurityContextHolderFilter 会以空 DeferredContext 重装 holder，授权环节必然拿不到认证；② Spring Security 6.5 的 holder 存原始 Supplier（无 memoization，sources 核实），仅对 `getContext()` 返回实例做 setAuthentication 变异的写法在异步窗口本就脆弱。
- **加固**：JwtAuthenticationFilter 覆写 `shouldNotFilterAsyncDispatch()=false`，并按官方模式整体写入——`SecurityContextHolder.setContext(context)` + `securityContextRepository.saveContext(context, request, response)`（RequestAttributeSecurityContextRepository，SecurityConfig 以 `.securityContext(c -> c.securityContextRepository(...))` 同源接线，保证 save 与 deferred 读取同源）。实测：修复前每条流 2 条 ERROR，修复后 0。
- **升格理由**（用户确认）：SSE 并发下 SecurityContext 丢失导致 401 是 M1 阶段最核心的架构级难点，涉及 JWT 过滤器与安全上下文持久化的底层机制，须正式记录。
- **文档动作**：04 §3.1"SSE 超时三维度对齐"注之后新增段落（P11）。

### A2 · 测试脚本 bash `&` 优先级（假 bug，误诊 1.5 小时）

`TOKEN=$(...) && (curl 流式) & curl 第二条` 中 `&` 优先级低于 `&&`——赋值链整体进入后台子 shell，主 shell 的 `$TOKEN` 为空，curl 发出 `Authorization: Bearer `（尾随空格被裁成 6 字符 "Bearer"）→ 401。应用行为始终正确（对空 token 静默跳过 → 匿名 → 401 是预期）。教训：测试脚本变量赋值独立成句；并发验证先 `curl -v` 看出站头再下结论。

### A3 · 重启残留僵尸实例双抢 8080

Windows SO_REUSEADDR 允许多实例共存监听同一端口，请求随机分流加剧误诊。教训：重启前 kill 全部 java 进程，并 `netstat -ano | findstr :8080` 核对单监听。

### A4 · Git Bash GBK 与中文日志

grep 中文模式匹配 UTF-8 日志文件会静默无命中（曾因此漏看一条关键 WARN）。教训：日志过滤用 ASCII 关键字（WARN/ERROR/类名）。

### A5 · SSE 建连前业务错误（HTTP 200 信封）被流消费器静默吞掉（M1-6 批次 5）

本项目业务错误统一 HTTP 200 + `{code,message}` 信封（GlobalExceptionHandler），SSE 接口**建立前**的错误（40902 会话已结束 / 42901 并发门 / 50002 上游异常）同样走此通道；建立后才走 error 事件（总体设计 §5.5 边界）。`utils/sse.ts` 原实现仅处理 `!resp.ok`——把 200 信封当流读取，找不到 `data:` 行后静默结束，用户侧表现为"消息发出后永远没有回应"。修法：读流前检查 `Content-Type`，`application/json` 则解析信封抛 `onError`（42901/50002 → `retryable=true`；401/40101 清 token 回登录页）；流内单帧 `JSON.parse` 加 try/catch 防御残帧。教训：04 §5.3 的规格示例代码本身带同样盲区，M1-5 的 curl 验证只覆盖了 happy path——**错误路径必须实测**。
