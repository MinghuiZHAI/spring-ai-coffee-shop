## 0. 选型原则与版本口径

1. **模块化单体**：一个 Spring Boot 应用 + MySQL + Redis，单机 Docker Compose 编排。凡引入分布式组件（MQ、注册中心、独立检索集群）无法给出与规模匹配的收益即排除。
2. **版本锁定原则**：主/次版本锁死，补丁版本随官方安全补丁跟进。本文版本号为撰写时点（2026-09）的稳定版本，实施时以官方仓库最新 GA 核对一次。
3. **排除清单（硬性约束）**：Kafka、Elasticsearch、K8s、Nacos、Sentinel、RocketMQ 全部不采用（理由见 §12.3）。
4. **预留哲学延续**：PRD v1.2 中"人工转接三层预留"（数据层枚举 / SessionRouter / 前端 role 多分支）在本次选型中逐一落实，见 §5 #17、§8 #25、§9 #29 与 §13 核对表。

## 2. A · 基础框架

| #    | 技术名称         | 版本号     | 在本项目中的用途           | 选型理由（为什么选它而不是替代方案）                       |
| ---- | ------------ | ------- | ------------------ | ---------------------------------------- |
| 1    | JDK          | 21（LTS） | 全项目运行时             | **21 而非 17**：本项目是典型的 IO 密集型应用（SSE 长连接挂起 + AI 流式响应等待 + 工具调用外部查询），JDK 21 虚拟线程（`spring.threads.virtual.enabled=true`）让每个 SSE 连接的挂起成本从"占一个平台线程"降为可忽略，这是 17 给不了的直接收益；此外 record、switch 模式匹配简化 DTO 与枚举分支代码。两者同为 LTS，升级风险为零，没有理由停在 17 |
| 2    | Spring Boot  | 3.5.5   | 应用框架、自动装配、Actuator | 3.5 是当前 OSS 维护主线；Spring AI 1.0 GA 的官方兼容基线是 Boot 3.4/3.5，选 3.5 而非 3.4（OSS 支持期已过）或 4.0（过新，第三方 starter 生态未跟进）。补丁号随 3.5.x 线跟进 |
| 3    | Maven        | 3.9.x   | 构建与依赖管理            | 国内 Java 岗位与 Spring 官方示例（含 Spring AI Alibaba 全部 demo）的事实标准；面试官打开 pom.xml 即可读。Gradle 的构建性能优势在单模块项目上以秒计，不值得引入一套新心智 |
| 4    | MyBatis-Plus | 3.5.12  | 全部业务表 CRUD、分页、乐观锁  | **对比 Spring Data JPA**：(a) 订单/积分流水/统计类查询直接写 SQL，不与 JPQL/派生查询较劲；(b) 国内主流，面试沟通零翻译成本；(c) 内置插件恰好逐条命中本项目需求——分页插件（订单/会话列表）、乐观锁（订单状态并发流转，配合 3.4 状态机）、自动填充（created_at/updated_at）、逻辑删除；(d) JPA 的收益只剩简单 CRUD 提速，复杂查询最终仍要回 native SQL。代价是无 schema 自动建表，由 Flyway（#20）承担 |

## 3. B · AI 能力层（核心）

| #    | 技术名称              | 版本号                                      | 在本项目中的用途                                 | 选型理由（为什么选它而不是替代方案）                       |
| ---- | ----------------- | ---------------------------------------- | ---------------------------------------- | ---------------------------------------- |
| 5    | Spring AI Alibaba | 1.0.0 GA 系列（如 1.0.0.2），基于 Spring AI 1.0.0 | ChatClient、ChatModel、EmbeddingModel、向量库抽象的实现层 | **与底层 SDK 的关系**：依赖方向为 业务代码 → ChatClient/ChatModel（Spring AI 抽象）→ spring-ai-starter-model-dashscope（Spring AI Alibaba 实现）→ dashscope-sdk-java（阿里原生 SDK，仅作底层传输）。业务代码零接触原生 SDK。选它而非裸 DashScope SDK：保留抽象层，未来换/加模型厂商不动业务代码；而非裸 OpenAI 兼容接口：官方维护的 qwen 特性适配（工具调用、流式语义）开箱即用 |
| 6    | 对话模型              | qwen-plus（主力）；qwen-turbo（会话摘要/标题等轻任务）    | 客服对话、意图理解、工具调用决策                         | 三档定位：qwen-max 强推理高成本，qwen-plus 能力与成本均衡，qwen-turbo 快而轻。**选 plus 做主力**：本项目问题域（菜单/订单/会员问答 + 只读工具调用）不涉及复杂推理，plus 的工具调用稳定性足以支撑 PRD 的"工具调用成功率 ≥95%"目标；成本约为 max 的 1/3、turbo 的 2~3 倍（量级参考，以百炼控制台实时价目为准）。按日均 1000 次会话、单次约 2K tokens 估算，plus 月成本在几十元量级，个人项目完全可承受。模型名走配置（`spring.ai.dashscope.chat.options.model`），评测集可横向对比后调整 |
| 7    | 嵌入模型              | text-embedding-v3（1024 维）                | 知识库文档与用户问题的向量化                           | 中文语义检索效果好；支持批量嵌入；单价低——本项目知识库分块总量 <300 块（见 #13 规模测算），全量嵌入一次成本 <0.1 元。1024 维需与 Redis Stack 建索引时的维度参数一致（写入 application.yml 统一管理）。若后续百炼推出新版本嵌入模型，注意维度变化需同步重建向量索引 |
| 8    | ChatClient 抽象     | Spring AI 1.0.0                          | 所有对话/流式/工具调用的统一入口                        | **而非直接调 DashScope SDK**，四个理由：(a) 面向抽象——业务代码只依赖 `ChatClient` 接口，评测时切换模型甚至厂商是改配置不是改代码；(b) Advisor 链——多轮记忆、RAG 上下文注入、调用日志都以 Advisor 机制挂载，横切能力不侵入主流程；(c) 统一 API——同步/流式/工具调用/结构化输出同一套编程模型；(d) 可测试——ChatClient 可 mock，AI 层可以脱离真实模型做单测。直接用 SDK 则以上全部自研且永久绑定厂商 |
| 9    | 流式输出              | SseEmitter（Spring MVC）+ JDK 21 虚拟线程      | 聊天窗口打字机效果（服务器→客户端单向流）                    | **对比 WebFlux 的 Flux**：本项目持久层是 MyBatis（阻塞 JDBC），WebFlux 下任何一次阻塞调用都会卡死 event loop——要么全栈 R2DBC（MyBatis 不支持），要么把阻塞调用池化调度（复杂度反噬、心智负担全部买断）。本场景只需要单向服务器推送，SSE 语义刚好，SseEmitter 编码直观。虚拟线程解决"每连接挂起一线程"的伸缩顾虑。注意：服务端内部 ChatClient.stream() 返回的 Flux 照常使用，只是出口逐 token 转发进 SseEmitter，二者不冲突 |
| 10   | Function Calling  | Spring AI @Tool 注解（1.0 工具体系）             | 实现 7 个只读工具：查订单/预计完成时间/退款进度/积分/优惠券/门店/推荐  | **对比手动拼接 JSON Schema**：@Tool 声明式——方法即工具，参数类型安全绑定，框架自动生成 Schema、解析模型返回、执行方法、回填结果；手动拼接则每加一个工具要改三处（Schema 串、解析器、分发器），无编译期检查，错一个字段名只在运行时爆。7 个工具 = 7 个带注解的方法，M3 新增工具零框架改动。全部工具只读，与 PRD"写操作边界"一致 |

## 4. C · RAG 链路

### 4.1 选型表

| #    | 技术名称 | 版本号                                      | 在本项目中的用途                     | 选型理由（为什么选它而不是替代方案）                       |
| ---- | ---- | ---------------------------------------- | ---------------------------- | ---------------------------------------- |
| 11   | 文档解析 | 只支持 Markdown，解析用 commonmark-java 1.x     | 知识库语料（菜单/活动/会员规则/FAQ/品牌）入库解析 | **MVP 只支持 Markdown**：PRD 第 8 节明确语料全部由本项目自己产出，格式 100% 可控；按 Markdown 标题树解析即得结构。排除 PDF/Word 解析（Tika/POI）——引入重量级依赖去解析根本不存在的输入是典型的 YAGNI 违背。后续迭代支持 PDF 时新增 DocumentParser 实现即可，接口先留 |
| 12   | 分块策略 | 结构感知分块：Markdown 标题层级切分 + 单块上限约 500 字符 + 相邻块 50 字符重叠；FAQ 一问一答独立成块 | kb_document → 向量化 chunk      | **对比纯固定长度**：会把一条 FAQ 从中间劈开，检索命中半问半答；**对比 embedding 语义分块**：每块边界都要调一次嵌入模型，成本和入库延迟翻倍，而 FAQ/规则型语料标题即语义边界，规则切分已够。选中间态：结构感知的规则分块 |
| 13   | 向量库  | Redis Stack（redis-stack-server 7.4），Spring AI RedisVectorStore 接入 | 存储知识库 chunk 向量，支持 KNN 检索     | **规模测算**：25 SKU + 30 FAQ + 2~3 个活动 + 品牌文档，分块后 <300 块，向量内存 <5MB。**为什么不需要 Milvus**：它是为亿级向量、分布式部署设计的专用系统，需要独立集群（外加 etcd、对象存储），运维复杂度与本项目规模差 5 个数量级。**为什么不用 pgvector**：业务库已定 MySQL，为 <300 条向量再引入一个 PostgreSQL 实例，多一份数据源运维，而"SQL 联查向量"的收益在本项目用不上。**为什么 Redis Stack 合适**：与 #15 的会话缓存复用同一个 Redis 实例，一个组件两用；此规模下性能绰绰有余；Spring AI 官方 RedisVectorStore 一键接入。规模若增长千倍再迁专用向量库，业务代码面向 VectorStore 抽象，迁移不动上层 |
| 14   | 检索策略 | 纯向量检索：topK=5 + 相似度阈值过滤（初始 0.5，评测集校准）+ 元数据过滤（按 kb_type：菜单/活动/会员规则/FAQ/品牌） | RAG 上下文召回                    | **MVP 选纯向量**：混合检索（向量+BM25）需要独立倒排索引组件——Elasticsearch 在排除清单里，MySQL ngram 全文索引中文效果一般且融合排序要自研。FAQ/菜单型语料的用户问法与文档措辞重合度高，纯向量召回预计达标；评测集（PRD §5）会验证，知识问答准确率 <85% 时再升级混合检索，届时加一个 Retriever 实现即可 |

### 4.2 与 PRD 预留项的衔接（数据层）

知识库 chunk 携带 `kb_type` 元数据用于过滤；chunk 归属的 `kb_document` 含**状态与版本字段**（PRD §7），文档更新即按 id 全量重建该文档向量，不做增量 patch——MVP 规模下重建成本可忽略（见 #24）。

## 7. F · 认证与权限

| #    | 技术名称  | 版本号                                      | 在本项目中的用途                                 | 选型理由（为什么选它而不是替代方案）                       |
| ---- | ----- | ---------------------------------------- | ---------------------------------------- | ---------------------------------------- |
| 21   | JWT 库 | jjwt 0.12.6                              | 登录态签发与校验                                 | **对比 auth0 java-jwt**：jjwt 0.12.x API 重构后更现代（builder/parser 链式），国内资料与社区讨论最多，HS256/RS256 与 JWE 全支持；auth0 库更小巧但功能面窄。**策略**：access token 2h（无状态，header 携带）+ refresh token 7d（Redis 白名单 `auth:refresh:{userId}:{jti}`，登出/改密即删，实现可吊销）；不引入 Spring Authorization Server——OAuth2 全家桶对本场景是过度设计 |
| 22   | 权限校验  | Spring Security 6（SecurityFilterChain + 方法级 @PreAuthorize） | 基于 user.role 字段的 USER / ADMIN / AGENT 三角色鉴权 | 角色 map：user.role → authorities 前缀 `ROLE_`。**三条路由规则**：`/api/user/**`（点单、订单、聊天）→ hasAnyRole('USER','ADMIN','AGENT')；`/api/admin/**`（知识库管理后台）→ hasRole('ADMIN')；`/api/agent/**` → hasRole('AGENT')——**MVP 无任何路由挂在此前缀下，规则先行占位，M3 坐席接口即插即用**（延续 PRD 预留哲学）。敏感服务方法上加 @PreAuthorize 兜底。聊天接口要求登录——AI 查"我的订单/积分"的前提是请求上下文带用户身份，同时天然满足"严禁越权查询他人数据"（PRD §6） |

## 12. 硬性约束决策

### 12.1 Prompt 模板：常量类集中管理，不入数据库

Prompt 全部硬编码在 `com.atlantic.coffee.ai.prompt.Prompts` 常量类（SYSTEM_PROMPT、RAG_ANSWER_TEMPLATE、RECOMMEND_TEMPLATE、FALLBACK_REPLY、TRANSFER_HINT），统一入口、只此一处。

**理由**：(a) prompt 与代码同受 git 管控——每次 prompt 调整有 diff、有 commit message、可回滚，这份"prompt 演进史"本身就是面试素材；(b) 零 IO、零缓存失效问题；(c) MVP 无多租户、无运营侧动态调参需求，入库是给不存在的要求买单；(d) 评测集直接针对常量跑回归。

**代价与迁移路径**：改 prompt 需重新部署，个人项目可接受；Prompts 是唯一引用点，未来若需动态化，引入 PromptProvider 接口包装，调用方不动——与本项目"接口预留"哲学一致。

### 12.2 饮品推荐：规则筛选，不做协同过滤 / embedding 相似度（边界声明）

MVP 推荐工具的实现为**基于规则的筛选**：按用户表述解析出的约束（口味标签、温度、价格带、品类）过滤 product 表（含 product_tags 字段），规则评分排序（命中活动加权重），返回候选列表后**由 LLM 只负责组织成自然话术，不负责筛选本身**。

**明确不做的**：协同过滤（无用户行为数据，冷启动不成立）；embedding 相似度推荐（菜单 <30 个 SKU，规则结果完全可解释、可单测）。此边界写死在代码注释与本文档，后续有行为数据积累再评估。

### 12.3 排除清单逐项理由

| 排除项              | 一句话理由                                    |
| ---------------- | ---------------------------------------- |
| Kafka / RocketMQ | 无服务间异步解耦与削峰需求；同步调用 + @Scheduled 轮询已覆盖全部场景 |
| Elasticsearch    | 数据量 <300 块 + <10 QPS，检索用 Redis Stack 向量检索即可 |
| K8s              | 单机单应用，Docker Compose 足够，K8s 纯增加运维负担      |
| Nacos            | 单应用无服务发现需求，配置用 application.yml + profile |
| Sentinel         | 个位数 QPS 无熔断限流场景                          |
