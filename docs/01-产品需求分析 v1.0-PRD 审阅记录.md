# PRD 审阅记录 · 01-产品需求分析 v1.0



## 一、我觉得有问题、需要在进入下一步之前修掉的地方

### 1. "发起退款申请"不该进 MVP

退款背后是一整套多状态、多角色、带资金语义的业务流。真要实现，至少要回答清楚：

- 什么订单状态下可以退款？

- 退到哪？余额还是原路？

- 谁来审核？

- 审核通过之后，积分和优惠券怎么回滚？

  ​

**我的决定**：MVP 里把 AI 客服的退款能力降级为"查询退款进度 + 退款规则问答"。
真正发起退款的按钮，留给业务系统的订单详情页。
AI 客服负责解释和查状态，不负责动钱。

### 2. "取消订单"和"退款"的边界是模糊的

订单未支付时可以取消，这个没问题。
但"待制作"状态下取消，会不会涉及退款？退款又和上面那个问题缠在一起。

**我的决定**：这两条业务规则需要在 PRD 阶段就确定好。
我打算在 PRD 里补一个订单状态机：

待支付 → 已支付(待制作) → 制作中 → 待取餐 → 已完成

然后明确每个状态下"取消"和"退款"是否可用。
不然后面做详细设计的时候，订单状态机会前后不一致。

### 3. 运营人员和 C 端用户共用一套认证体系吗？

PRD 里有两个角色需要登录：
- C 端顾客：手机号 + 密码（模拟验证码）
- 店铺运营：要进知识库管理后台

但我只写了 C 端的登录方式。运营人员怎么登录？
是同一张 user 表加 role 字段，还是单独做一张管理员表？

**我的决定**：MVP 阶段用同一张 user 表 + role 字段（CUSTOMER / OPERATOR）。
JWT 里带上角色，后台接口用 Spring Security 的角色校验拦截。
这个决定会直接影响技术栈里权限框架的选型，所以必须在阶段二之前定下来。

### 4. "催单"在 MVP 里其实是个空动作

"催单/取餐码"这一项，取餐码只是订单状态的展示，属于查询。
但"催单"是一个写操作——它的语义是"通知门店"。

在没有真实门店系统的情况下，催单只能是一个安慰性话术。
如果 AI 回复"已为您催单"，后台其实什么都没发生，演示的时候会很假。

**我的决定**：MVP 里把"催单"降级成"查询预计制作时间 + 告知取餐码"。
或者干脆在 PRD 里写明"催单为模拟动作，仅记录日志"。

### 5. "首 token < 2s"这个指标可能定得太乐观

Qwen 系列的首 token 延迟通常在 1–3 秒。
再加上 RAG 检索（向量检索 + 重排）和可能的 Function Calling 往返，2 秒的首 token 目标在阿里云百炼上有一定风险。

**我的决定**：把指标改成"P95 首 token < 3s"，
并且区分"纯对话"和"带工具调用"两种情况。

### 6. PRD 里缺一份核心实体清单

PRD 的功能描述很完整，但没有实体清单。
User、Product、Order、OrderItem、Coupon、UserCoupon、Cart、PointAccount、KnowledgeDocument 这些实体的字段和关系，至少要在进入技术栈确定之前有个初稿。

不然阶段二讨论"用什么向量库"的时候，我连要存什么都不知道。

**我的决定**：在 PRD 末尾补一节"核心数据实体（初稿）"。
每个实体列出关键字段和关系，不需要 DDL 级别，
但要有 `Order 1:N OrderItem`、`User N:M Coupon（通过 UserCoupon）` 这种关系描述。
