# 总体设计 v1.1 审阅记录



### 问题 1：RAG 检索范围与 kb_type 枚举不匹配（架构缺口）

§4.1 的 Agent 矩阵里，OrderAgent 的 RAG 检索范围写的是 **"FAQ（退款/取消规则类）"**，
CouponAgent 写的是 **"会员规则、活动"**。

但 PRD §7 里 `kb_document.kb_type` 的枚举值是：**菜单 / 活动 / 会员规则 / FAQ / 品牌**。

问题：
- OrderAgent 想检索的是 **FAQ 这一大类里的子集**（退款/取消规则），但 kb_type 只到 FAQ 这一层，根本无法区分"退款 FAQ"和"会员 FAQ"。
- CouponAgent 要检索"会员规则 + 活动"两个 kb_type没问题，但 OrderAgent 的"FAQ 子集"在当前元数据模型下根本实现不了。

三种解法：

| 方案   | 做法                         | 成本   | 我的评价            |
| ---- | -------------------------- | ---- | --------------- |
| A    | OrderAgent 检索全部 FAQ        | 零成本  | 最简单，命中率略降但可接受   |
| B    | kb_document 增加 sub_type 字段 | 小    | 最精确，但增加元数据管理复杂度 |
| C    | 把 FAQ 拆成多个 kb_type         | 中    | 枚举膨胀，改动面大       |

**我的决定**：MVP 选方案 A。理由是 FAQ 总量只有 30+ 条，分块后约 50-80 块，全部召回也不会污染上下文，靠 System Prompt 的职责边界条款过滤不相关内容就够了。未来 FAQ 规模增长再升级到方案 B。

必须在文档里显式写出来，不能让它成为实现阶段的随机选择。



### 问题 2：会话结束逻辑缺失（架构缺口）

PRD v1.2 §3.2 和 §3.4 明确定义了 `chat_session.status` 的三个值：`AI_SERVING / HUMAN_SERVING / ENDED`。

但总体设计里**没有描述会话如何进入 ENDED 状态**：

- §5.2 API 列表里**没有"结束会话"接口**
- §3.2 调用时序里没有会话结束的处理逻辑
- §2.1 包结构中 `ai.session` 提到"会话创建、历史游标分页"，但没有"会话结束"

这就尴尬了：`ENDED` 这个枚举值虽然存在，但实际上没有任何代码路径会产生这个状态。
它会变成一个**永远不出现的死枚举**。

**我的决定**：MVP 用"定时任务 + 主动关闭接口双保险"。

- 定时任务：`@Scheduled` 每分钟扫描 `updated_at < NOW() - 30min` 且 `status != ENDED` 的会话，批量置为 ENDED。
- 主动关闭接口：`POST /api/user/chat/sessions/{id}/close`，用户主动关闭窗口时调用。

定时任务是兜底（防止用户直接关浏览器不触发接口），接口是正常路径。



### 问题 3：意图分类失败的降级策略未定义（健壮性）

§3.2 第 5 步描述了 IntentAgent 用 qwen-turbo 分类。但如果：

- LLM 返回的 JSON 格式错误（模型不稳定时很常见）
- LLM 超时（百炼偶尔会）
- 返回的 intent 值不在枚举范围内

**文档里没有任何描述这些情况如何处置**

**我的决定**：

- JSON 解析失败：重试一次，仍失败则降级为 `KNOWLEDGE`（交给 FaqAgent 兜底）
- LLM 超时：跳过意图分类，直接走 FaqAgent（最通用的 Agent）
- intent 值非法：同样降级为 `KNOWLEDGE`
- 降级事件需要落库，用于分析意图分类的实际成功率
